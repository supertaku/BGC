# M21–M22 — Final QA and Production Release

## Mission

Assume M16–M20 have all PASSED.

The project is now:

* geographically complete across the BGC working area;
* interactively explorable;
* spatially streamed;
* LOD-aware;
* visually polished;
* usable on desktop and mobile;
* productized;
* performance-hardened.

Do NOT add major features from this point onward.

The remaining sequence is:

```text
M21
DISTRICT-WIDE QA + CORRECTION

        ↓ RELEASE GATE

M22
PRODUCTION RELEASE
```

Primary model:

SOL

Routine validation, reports, build/test execution, asset checks and deterministic fixes may use lighter models/scripts.

Astra:

NO by default.

Use Astra only if M21 discovers a severe landmark-specific visual defect that cannot reasonably be fixed with the established Sol workflow.

## 36. Inspect post-M21 application capabilities before choosing hosting

Do NOT choose a provider based on preference alone.

Determine whether the app uses:

```text
server-only Next.js features
Route Handlers
dynamic server rendering
server actions
image optimization
runtime environment variables
```

Then select a supported deployment model.

Current Next.js supports:

```text
Node.js server
Docker
static export
platform adapters
```

but static export has limited Next.js feature support.

Therefore:

```text
if static export fully supports actual app
→ static hosting is valid

otherwise
→ Node/Docker/managed Next.js platform
```

Do not force static export merely because the application is mostly client-side.

## 49. HTTPS

Production must use HTTPS.

## 50. Self-hosting requirements if chosen

If self-hosting Next.js:

place a reverse proxy in front of the Node server.

Current Next.js guidance recommends this so malformed requests, rate limits, slow connections and similar concerns are handled before reaching the app server.

This requirement does not apply identically to managed Next.js hosts that provide this layer.
