# M20 — Mobile, Performance & Resilience Hardening

## Mission

Assume M16–M19 have all PASSED.

The product now already has:

* complete BGC geographic massing;
* dynamic tiles;
* LOD2 city;
* priority LOD1 landmarks;
* street environment;
* improved PBR materials;
* lighting and visual polish;
* search;
* place information;
* deep linking;
* walking;
* tours;
* responsive product UI;
* accessibility work;
* production build.

M20 must NOT add another major product feature.

The goal is:

> Make the existing BGC experience load efficiently, remain responsive, degrade gracefully, and work reliably across realistic desktop and mobile hardware.

The optimization rule is:

```text
MEASURE
   ↓
IDENTIFY BOTTLENECK
   ↓
CHANGE ONE SYSTEM
   ↓
MEASURE AGAIN
   ↓
KEEP / REVERT
```

Do not optimize based on intuition alone.

Primary model:

SOL

Routine benchmarking, asset processing, compression trials and report generation may use lighter agents/scripts.

Astra:

NO.

---

# 1. Inspect the actual post-M19 repository

Do not assume the current conversation accurately describes every M19 implementation detail.

Before changing anything:

* inspect the final M19 commit;
* inspect `package.json` and lockfile;
* inspect M18/M19 reports;
* run production build;
* inspect current quality settings;
* inspect current loader/cache architecture;
* inspect texture inventory;
* inspect GLB inventory;
* inspect current mobile controls;
* inspect current bundle output.

Do not upgrade dependencies simply because newer versions exist.

Record the actual baseline.

# 3. Build a real-device test matrix

Do NOT use Chrome DevTools mobile emulation as the sole mobile benchmark.

Use actual hardware.

At minimum require:

```text
1 real desktop/laptop
1 real mobile device
```

If the intended supported platforms include both Android and iOS:

test:

```text
Android + Chrome
iPhone/iPad + Safari
```

on physical hardware before release.

If a platform is unavailable, report:

```text
NOT TESTED
```

rather than claiming support.

Browser/device emulation may supplement these tests but cannot replace them.

---

# 4. Do not invent a universal FPS target

Record actual device refresh rates and observed performance.

Define supported-device acceptance after obtaining baseline measurements.

Separate:

```text
IDEAL
ACCEPTABLE
UNSUPPORTED / DEGRADED
```

for each tested hardware tier.

Do not change the performance target after optimization merely to make the milestone pass.

---

# 5. Create a performance profile system

Implement a small quality system:

```text
AUTO
LOW
HIGH
```

Add `MEDIUM` only if measurements show it is useful.

Default:

```text
AUTO
```

Allow the user to override Auto.

Persist a user-selected override locally.

Do not base quality solely on user-agent strings.

---

# 6. AUTO quality should respond to observed performance

Use measured runtime behavior.

R3F/Drei performance monitoring may be used to detect sustained:

```text
performance decline
performance recovery
```

Use hysteresis.

Do NOT change quality every few frames.

Concept:

```text
performance remains poor
        ↓
reduce one quality level

performance remains healthy
        ↓
optionally increase quality
```

Avoid:

```text
HIGH
LOW
HIGH
LOW
```

oscillation.

---

# 7. Adaptive DPR

DPR should become one of the first adjustable GPU-cost controls.

Do not automatically render every phone at full:

```text
window.devicePixelRatio
```

High-DPR phones may require substantially more rendered pixels.

Establish empirically tested:

```text
minimum DPR
maximum DPR
```

for AUTO mode.

Do not hard-code values from this prompt.

Measure visual quality and frame cost on the actual test phones.

---

# 8. Prefer DPR reduction before destroying scene fidelity

When GPU-bound, first test reducing:

```text
render resolution
```

before aggressively removing:

```text
buildings
important landmarks
major environment objects
```

A slight reduction in pixel density may be less noticeable than losing geographic context.

Measure this.

---

# 9. Adaptive quality knobs

AUTO may control combinations of:

```text
DPR
shadow quality
shadow distance
environment detail
texture resolution
anisotropy
LOD1 activation distance
tile preload distance
simultaneous asset loads
```

Do NOT dynamically change all parameters simultaneously.

Adjust gradually so benchmark results identify which change mattered.

---

# 10. Preserve geographic accuracy across quality levels

LOW mode may reduce:

```text
visual quality
shadows
texture resolution
secondary props
LOD1 range
```

but should NOT change:

```text
building position
road position
BGC geometry
canonical entity identity
verified height values
```

Performance settings must not create a geographically different city.

---

# 11. Mobile input must not depend on pointer lock

Desktop WALK can continue using pointer lock.

Touch WALK requires a separate interaction path.

Prefer a simple model such as:

```text
left touch region
→ movement

right touch region
→ camera look

explicit UI controls
→ exit / sprint where necessary
```

Implement using Pointer Events or the existing compatible input abstraction.

Do not emulate mouse pointer lock on touch.

---

# 12. Mobile WALK controls

Requirements:

```text
frame-rate-independent movement
multi-touch-safe
no accidental page scrolling while controlling
clear exit button
clear movement state
usable in landscape
usable in portrait where practical
```

Do not make users perform tiny gestures.

Use appropriately sized controls from M19's accessibility system.

---

# 13. Touch interaction conflicts

Test interaction between:

```text
camera movement
building selection
UI panels
search
tour controls
virtual movement controls
browser scrolling
```

Touching UI must not rotate the camera.

Touching movement controls must not select buildings.

Dragging to look must not unintentionally activate place information.

---

# 14. Device capability signals

Useful signals may include:

```text
hardwareConcurrency
viewport size
DPR
observed FPS
WebGL capabilities
```

`deviceMemory` may be used as an optional hint only where available.

Do NOT make it a required input.

Do NOT assume reported CPU count or memory precisely represents physical hardware.

Observed runtime performance should carry more weight.

---

# 15. Determine CPU-bound vs GPU-bound cases

Use measurements to distinguish bottlenecks.

Likely GPU indicators include improvements after reducing:

```text
DPR
shadows
texture cost
```

Likely CPU/draw-call indicators include improvement after reducing:

```text
draw calls
scene traversal
tile changes
interaction work
```

Do not assume the bottleneck before testing.

---

# 16. Profile render-loop work

Audit every `useFrame`.

Check for:

```text
React setState calls
temporary object allocation
array creation
new Vector3 / Matrix4 every frame
expensive searches
full-building collision scans
DOM work
```

R3F frame-loop work should remain imperative and lightweight.

Reuse temporary:

```text
Vector2
Vector3
Matrix4
Box3
Ray
```

objects where practical.

---

# 17. Maintain spatial collision efficiency

Walking collision must continue querying only relevant nearby spatial data.

Do not scan all ~7,000 buildings every frame.

Measure collision cost on mobile.

If necessary:

```text
current tile
+
neighboring collision regions
```

should constrain work.

Do not introduce a physics engine unless measured requirements justify it.

---

# 18. Inspect idle rendering

Walking and tours require continuous rendering.

Static inspection may not.

Evaluate:

```text
frameloop = demand
```

or equivalent idle rendering during stationary Inspect mode.

If implementing it:

```text
camera movement
UI interaction
LOD change
tile arrival
tour transition
```

must correctly invalidate the frame.

Only keep this optimization if it materially reduces device work without causing stale frames.

---

# 19. Pause unnecessary work when hidden

When the browser tab/app becomes backgrounded:

avoid unnecessary application-level calculations.

Ensure returning to the page restores:

```text
camera
tiles
LOD
selection
quality state
```

correctly.

Do not rely on hidden-tab FPS benchmarks; browsers intentionally throttle background animation.

---

# 20. Inventory all post-M18 textures

Produce:

```text
texture name
dimensions
format
bytes
mipmaps
material usage
number of assets sharing it
```

Identify:

```text
duplicate textures
oversized textures
textures used far below native resolution
```

Do not compress blindly.

---

# 21. Verify texture reuse

Shared city materials should reuse shared textures rather than duplicate image data across many assets.

Prioritize reuse for:

```text
asphalt
sidewalk
grass
soil
concrete
stone
generic glass support maps
```

Where practical, avoid packaging duplicate copies inside multiple GLBs.

---

If M18 textures become a meaningful:

Compare:

```text
original textures

KTX2
```

on actual mobile hardware.

Record:

```text

visual quality
load time
```

Use KTX2 only if benefits justify decoder/transcoder complexity.

---

# 23. Preserve correct texture color spaces

When optimizing textures:

preserve correct treatment of:

```text
base color
emissive
normal
roughness
metalness
AO
```

Do not allow compression tooling to change material appearance unintentionally.

Run visual regression.

---

# 24. Mipmaps

Ensure appropriate 3D textures have sensible mipmaps.

This is especially important for:

```text
roads
ground
building surfaces
```

viewed at large distance ranges.

Do not ship unnecessary oversized texture levels if they provide no visible benefit.

---

# 25. Anisotropy

Do not automatically use maximum anisotropy everywhere.

Ground and road surfaces may benefit from it at oblique viewing angles, but higher anisotropy increases sampling cost.

Benchmark:

```text
LOW
AUTO
HIGH
```

settings if necessary.

---

# 26. Geometry compression experiment

Do NOT automatically select Draco or Meshopt.

Three.js GLTFLoader supports both.

Take representative assets:

```text
one dense LOD1 landmark
one ordinary LOD1
one large city tile
one small tile
```

Produce:

```text
uncompressed
Meshopt
Draco
```

versions where the export pipeline supports them.

Compare on actual mobile hardware:

```text
file bytes
download time
decode time
time until visible
memory
visual equivalence
```

Choose:

```text
NONE
MESHOPT
DRACO
```

based on measured total experience.

Do not select solely by smallest file.

---

# 27. Avoid double compression complexity

Do not stack unrelated geometry compression systems without a clear benefit.

The goal is:

```text
lowest practical total load cost
```

not:

```text
smallest GitHub file
```

Decoder cost matters on weaker CPUs.

---

# 28. Tune tile loading

Current spatial streaming should be reassessed on mobile.

Measure:

```text
active radius
preload radius
retention radius
number of active tiles
tile bytes
load concurrency
```

Do not assume desktop M12 values remain optimal.

---

# 29. Prioritize tiles intelligently

When multiple tiles require loading, prioritize approximately:

```text
current / immediately surrounding tiles
then
movement direction / visible region
then
remaining preload ring
```

Keep implementation simple.

Do not build a predictive streaming engine unless measurements require it.

---

# 30. Limit simultaneous decoding if necessary

Too many simultaneous GLB decodes may cause:

```text
main-thread stalls
memory spikes
mobile stutter
```

Measure asset-load concurrency.

If necessary, create a bounded load queue.

Do not arbitrarily serialize every request.

---

# 31. Tune landmark LOD

Mobile LOW/AUTO profiles may activate LOD1 closer to the user if high-detail assets are expensive.

Maintain:

```text
LOD hysteresis
geographic alignment
no visible scale jump
```

Do not disable important landmark detail unnecessarily.

---

# 32. Cache policy

M12 intentionally retained loaded assets because the original city was small.

After M17/M18 the asset set may be larger.

Measure actual post-M19 cache growth.

If memory remains healthy:

keep the simple cache.

If memory becomes problematic:

introduce bounded eviction.

Do not implement eviction preemptively.

---

# 33. Resource disposal

If bounded eviction is introduced:

verify disposal of:

```text
geometry
materials
textures
render targets
```

without destroying resources shared by still-active assets.

Do not assume removing an object from the scene automatically releases GPU memory.

---

# 34. Establish a memory budget

WebGL does not provide a portable exact VRAM query.

Therefore estimate memory from owned resources and real-device stability.

Track at minimum:

```text
renderer.info.memory.geometries
renderer.info.memory.textures
estimated texture bytes
loaded GLB bytes
active/cached asset counts
```

If useful, derive a conservative per-pixel/resource budget from tested devices.

Do not claim exact VRAM usage.

---

# 35. Context-loss handling

Mobile browsers may lose WebGL contexts under resource pressure.

Implement explicit handling for:

```text
webglcontextlost
webglcontextrestored
```

Provide user-facing recovery state rather than leaving a frozen canvas.

---

# 36. Test context loss deliberately

Use:

```text
WEBGL_lose_context
```

in development to simulate failure.

Verify:

```text
context loss detected
UI remains usable
user informed
renderer recovers or safe reload occurs
world state restored where practical
```

The application must not remain silently broken.

---

Run sustained physical-device tests.




# 46. Mobile UI performance

Inspect product UI separately from Three.js.

Look for:

```text
large backdrop filters
expensive blur

```

The polished M19 interface must not become a major mobile compositing cost.

Do not remove visual effects without measuring their impact.

---

# 47. Search/UI work must not affect the render loop

Ensure:

```text
search typing
place panel updates
tour UI
debug UI
```

do not cause the entire Canvas tree to rerender unnecessarily.

Keep fast 3D state separated from ordinary product state.

---

# 48. Progressive degradation order

If a device cannot maintain acceptable interaction, degrade approximately in this order, subject to measurements:

```text
1. lower DPR
2. lower/disable expensive shadows
3. reduce secondary environment detail
4. reduce expensive texture settings
5. tighten high-detail LOD range
6. adjust tile/cache behavior
```

Do not immediately remove core geographic massing.

---

# 49. User quality override

Users should be able to choose:

```text
Auto
Low
High
```

if M19 has an appropriate settings location.

Changing the setting should provide predictable behavior.

Do not hide all quality choices behind automatic heuristics.

---

# 50. Do not overfit one test device

An optimization that improves one phone but materially damages all others should not become universal.

Compare across the available matrix.

Device-specific behavior should be capability/performance-driven rather than hard-coded model names wherever possible.

---

Automated FPS measurements from background/throttled browsers must continue to be rejected as unreliable.

# 55. Do not start WebGPU migration

M20 is NOT a WebGPU migration milestone.

The current WebGL architecture is already proven.

Do not rewrite the renderer unless WebGL is demonstrated to be the actual blocking issue.

---

# 56. Do not add PWA/offline scope automatically

M20 is also NOT automatically:

```text
service worker
offline city caching
installable PWA
```

Those can be future product choices.

Do not complicate performance work with an unrelated caching architecture.

---

# 57. Do not add analytics as a performance dependency

Use local benchmark/debug tooling.

Real-user performance analytics may be considered at release, but M20 does not require third-party analytics.

---

# 58. Security/dependency upgrades

Do not perform unrelated major upgrades.

If the post-M19 Next.js/React/Three.js versions have an applicable critical security update, handle it separately and regression-test it.

Do not mix framework migration with optimization unless necessary.

## Device validation

[ ] desktop physical-device benchmark complete

[ ] at least one real mobile benchmark complete
