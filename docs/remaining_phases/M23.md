# Post-Release Improvement and Refinement Roadmap

## Goal

Improve BGC 3D incrementally without destabilizing the released product.

Every improvement cycle should follow:

```text
observe
→ identify highest-impact weakness
→ measure baseline
→ implement bounded improvement
→ regression test
→ release
```

Do not continuously rebuild the entire project.

---

## M23 — Feedback and Weakness Audit

Collect real evidence from the released product.

Review:

```text
user feedback
navigation friction
search failures
most-viewed buildings
tour usage
device performance
error logs
slow areas
visually weak areas
data inaccuracies
```

Produce a ranked improvement backlog.

Classify issues roughly as:

```text
CORRECTNESS
FIDELITY
UX
PERFORMANCE
CONTENT
DATA
ACCESSIBILITY
```

Prioritize by:

```text
user impact
frequency
severity
effort
confidence in solution
```

M23 should mostly diagnose rather than build.

---

## M24 — Geographic and Height Refinement

Improve the most noticeable low-confidence geographic data.

Target:

```text
important skyline buildings
tour-visible buildings
major roads/open spaces
obvious height outliers
incorrect building parts
important missing names
```

Do NOT attempt to verify all ~7,000 buildings.

Replace procedural values only where doing so materially improves the experience.

Track:

```text
VERIFIED
ESTIMATED
PROCEDURAL
```

before and after.

---

## M25 — Landmark Expansion

Promote additional high-value buildings:

```text
LOD2 → LOD1
```

Use the M16 ranking method again.

Choose a bounded batch, perhaps:

```text
5–10 buildings per release
```

based on actual user visibility and evidence readiness.

Do not detail buildings merely to increase the LOD1 count.

---

## M26 — Existing Landmark Refinement

Instead of adding buildings, improve existing important landmarks where QA shows visible weakness.

Examples:

```text
better podium geometry
entrance correction
roof silhouette
facade proportions
materials
street relationship
```

Use Astra only for individual visually difficult cases where:

```text
good references exist
+
Sol has already failed to resolve the discrepancy
```

## M28 — Surface and Material Refinement

Improve material fidelity where it gives visible benefit.

Focus on:


Potential additions:

```text

```

## M29 — Lighting and Atmosphere

```text
sunset

```

but only if performance remains acceptable.

Do not build a full time-of-day simulator unless it becomes a product goal.

Potential additions only if justified:

Focus on:

## M32 — Runtime and Asset Optimization

Only optimize if profiling identifies a real bottleneck.

Potential work:

```text

texture compression
Meshopt/Draco

cache eviction

bundle splitting
instancing
```

Never introduce compression or architectural complexity without measured improvement.

---

## M33 — Tours and Content Expansion

Expand the experience beyond the initial guided tour.

Possible themes:

```text
Bonifacio High Street
Architecture
Public spaces
Landmarks
North BGC
South BGC
```

Tour facts must remain evidence-grounded.

Do not turn the project into a generic tourism-content site.

---

## M34 — Data Refresh Pipeline

Eventually the city data will age.

Create a controlled refresh process for:

```text
OSM changes
new buildings
demolished buildings
renamed buildings
new roads
new POIs
```

Do not overwrite the existing release blindly.

Use:

```text
old snapshot
vs
new snapshot
→ diff
→ review
→ accept
→ regenerate affected tiles
```

Preserve reproducibility of old releases.

---

## M35 — Advanced Features, Only If Desired

Do not start them merely because the core project is finished.

# Improvement Priority Order

Default priority should be:

```text
1. correctness
2. major UX problems
3. major performance problems
4. high-value visual inaccuracies
5. landmark expansion
6. environment refinement
7. cosmetic polish
8. new features
```

Do not prioritize novelty over correctness.

---

# Release Strategy

After v1.0:

```text
v1.1
small corrections / UX / performance

v1.2
new landmark batch + environment refinement

v1.3
data refresh / new tour content

v2.0
only for a major product or architecture change
```

Avoid treating every small change as another massive milestone.

---

# Rule for Every Refinement Cycle

Before implementing:

```text
What is wrong?
Who notices it?
How often?
How do we measure improvement?
What could regress?
```

After implementing:

```text
Did it measurably improve?
Did performance regress?
Did grounding regress?
Did accessibility regress?
Did licensing change?
```

If there is no measurable benefit, revert or defer.

---

# Long-Term Target

The project should gradually move from:

```text
complete geographic representation
```

toward:

```text
increasingly accurate high-value areas
```

rather than attempting:

```text
maximum detail everywhere
```

That keeps the project maintainable, grounded, and performant.

# M23+ — Post-Release Improvement and Refinement Program

## Operating rule

M22 represents the completed v1 release.

Everything after M22 is post-release refinement.

Do NOT automatically execute M23 through M35 in sequence.

Treat them as candidate workstreams.

At the start of every refinement cycle:

1. inspect the current released build;
2. review known limitations, bug reports, user feedback, performance data, and visual/data QA findings;
3. rank the highest-impact weaknesses;
4. choose the smallest workstream or combination of workstreams that directly addresses those weaknesses;
5. define measurable acceptance criteria before implementation;
6. implement the bounded improvement;
7. rerun affected regression, performance, accessibility, geographic, and licensing checks;
8. release as an appropriate v1.x update;
9. stop and report results before beginning another refinement cycle.

Prioritize work in this order:

```text
1. correctness
2. severe UX problems
3. severe performance/reliability problems
4. high-value geographic or visual inaccuracies
5. important landmark improvements
6. street/environment refinement
7. cosmetic polish
8. new features
```

Do not add features merely because they appear later in this plan.

The objective is:

> Improve the released BGC experience where evidence shows the greatest user or fidelity benefit, while preserving geographic grounding, performance, accessibility, reproducibility, and licensing compliance.

Then use the M23–M35 workstreams below as the available refinement backlog.
