# M19 — BGC Product Experience and Final UI

## Mission

Assume M16–M18 have all PASSED.

The underlying product already has:

* complete BGC geographic massing;
* dynamic spatial tiles;
* LOD switching;
* first-person walking;
* collision;
* building selection;
* building search;
* guided tours;
* street environment;
* priority LOD1 architecture;
* improved materials;
* improved lighting;
* visually coherent environment;
* production-valid runtime.

M19 must NOT redesign the underlying 3D engine.

M19 must transform the engineering viewer into a polished public-facing product.

The question is now:

> Can a first-time user open the site and immediately understand what it is, explore BGC, find a place, inspect a building, take a tour, and recover from mistakes without knowing anything about the technical implementation?

Primary model:

SOL

Astra:

NO

---

# 1. Audit the actual post-M18 application first

Do not assume the GitHub `main` branch currently represents the post-M18 state.

Before modifying UI:

1. inspect the actual M18 commit/branch;
2. read M16–M18 reports;
3. run the production application;
4. inspect desktop and narrow/mobile layouts;
5. inventory existing controls;
6. identify temporary/debug UI;
7. identify duplicated functionality.

Do not design against old screenshots or conversation memory.

Create:

```text
docs/M19_UI_AUDIT.md
```

---

# 2. Remove milestone/debug framing from the public experience

The current committed UI still contains engineering language such as:

```text
M11 · geographic massing diagnostic
Whole-BGC low-fidelity skeleton
```

and metadata such as:

```text
BGC 3D Pipeline Viewer
Synthetic Blender-to-Three.js integration fixture
```

These are appropriate for development but not for the final user experience.

Replace public-facing copy with product-oriented language.

Keep engineering metrics available only through:

```text
?debug=1
```

or an equivalent development/debug mode.

Do not delete diagnostics that remain useful for M20 performance work.

---

# 3. Establish the product information architecture

Keep the main application centered on one 3D experience.

Recommended high-level structure:

```text
BGC 3D
│
├── Explore
│   ├── Inspect
│   └── Walk
│
├── Search
│
├── Places / selected building
│
├── Tours
│
└── Settings / Help
```

Avoid turning this into a multi-page content website.

The 3D city remains the product.

---

# 4. Product shell

Build a lightweight interface around the viewport.

Conceptually:

```text
┌──────────────────────────────────────────────┐
│ BGC 3D               Search       Controls   │
│                                              │
│                                              │
│                 3D WORLD                     │
│                                              │
│                                              │
│ [mode]                              [tools]   │
│                                              │
│ selected building panel / tour card          │
└──────────────────────────────────────────────┘
```

This is conceptual only.

Derive the actual visual composition from the M18 scene and current implementation.

Do not force this exact layout if it obstructs the 3D view.

---

# 5. Keep the 3D canvas dominant

The UI should support exploration rather than cover it.

Avoid permanent large panels.

Prefer:

* compact top controls;
* collapsible drawers;
* bottom sheets on narrow screens;
* temporary contextual cards;
* progressive disclosure.

Do not create a dashboard around the city.

---

# 6. First-entry experience

Replace the technical loading experience with a deliberate entry flow.

At minimum:

```text
BGC 3D
Explore Bonifacio Global City in 3D
```

Then:

```text
Explore
```

or an equivalent primary action.

Avoid a long marketing splash screen.

The user should reach the interactive city quickly.

---

# 7. Loading state

The city already loads incrementally.

Show meaningful state such as:

```text
Loading BGC…
Preparing nearby buildings…
Loading detailed landmarks…
```

Do not expose:

```text
94 GLBs
renderer.info
tile_004_007
```

to ordinary users.

Use progress only when it can be measured reliably.

Never display fake progress percentages.

---

# 8. First-use onboarding

Provide a short contextual onboarding flow.

Desktop:

```text
Drag → look around
Scroll → zoom
WASD → walk
Esc → exit walk mode
Click → inspect a building
```

Touch:

show only controls that actually work for the implemented touch experience.

Do not show a long tutorial modal.

Prefer a brief overlay that can be dismissed and reopened from Help.

Store dismissal locally if appropriate.

---

# 9. Navigation modes

Make the existing navigation states understandable.

Public terminology should be clear.

For example:

```text
Explore
Walk
Tour
```

rather than technical labels such as:

```text
OrbitControls
PointerLock
NavigationController
```

If `Inspect` remains clearer than `Explore`, retain it.

Test terminology in the actual interface.

---

# 10. Mode switching

Mode state must always be visible.

The user should never wonder:

> Why is my mouse suddenly controlling the camera?

When entering Walk:

show a temporary message such as:

```text
Walk mode
WASD to move · Shift to sprint · Esc to exit
```

When pointer lock ends:

the interface should clearly return to a non-locked state.

---

# 11. Search becomes a first-class product feature

Reuse the existing local building search.

Do not create a backend.

Implement a proper accessible searchable combobox.

Search across available:

```text
canonical name
aliases
known POI names
```

Potential result structure:

```text
Central Square
Shopping · High Street Central

W Global Center
Office · 30th Street
```

Only show categories supported by project data.

Do not invent descriptions.

---

# 12. Search behavior

Selecting a search result should:

```text
select entity
→ close results
→ transition camera appropriately
→ show entity information
```

Do not automatically enter Walk mode.

Allow keyboard operation:

```text
Arrow keys
Enter
Escape
```

Follow current WAI-ARIA combobox behavior.

---

# 13. Building information panel

When a building is selected, show a compact information surface.

Use only existing verified project data.

Potential fields:

```text
Building name
Building type
Height
Height evidence state
LOD/fidelity information only if useful
Short known description
```

Do NOT show internal IDs to normal users.

Keep them available in debug mode.

---

# 14. Communicate uncertainty appropriately

The project intentionally distinguishes:

```text
VERIFIED
ESTIMATED
PROCEDURAL
UNKNOWN
```

Do not expose raw engineering terminology everywhere.

For information users might interpret as factual, use understandable disclosure.

Example:

```text
Approx. height: 42 m
```

when estimated.

Consider a small:

```text
About the data
```

explanation for the reconstruction methodology.

Do not pretend procedural massing is surveyed architecture.

---

# 15. Place panel actions

Useful building actions may include:

```text
View
Walk here
Share
Close
```

Only implement actions that work reliably.

Do not add buttons purely for visual completeness.

---

# 16. Deep linking

Make meaningful product states shareable through the URL.

Use Next.js App Router search parameters.

Candidate state:

```text
?place=central-square

?mode=walk&place=central-square

?tour=high-street
```

Do NOT synchronize raw camera coordinates continuously into the URL.

That would create noisy URLs and unnecessary history updates.

Persist only meaningful semantic state.

---

# 17. Restore shareable state

Opening a shared place URL should:

```text
load app
→ resolve entity
→ position useful camera
→ select entity
```

Opening a tour URL should:

```text
load app
→ prepare tour
```

Do not automatically trigger pointer lock because browser security requires explicit user interaction.

---

# 18. Share action

Implement a simple share mechanism.

Primary output:

```text
copy current semantic deep link
```

Use native sharing only where browser support and UX make sense.

Always retain copy-link fallback.

Do not make sharing dependent on a third-party service.

---

# 19. Tours

M13 already provides a seven-stop guided tour.

M19 should improve the product presentation of tours, not rebuild the camera engine.

Provide:

```text
tour title
short description
number of stops
start
next
previous
exit
progress
```

Example:

```text
3 / 7
Central Square
```

---

# 20. Tour interruption

Users must be able to:

```text
pause / exit
select another building
switch navigation mode
```

without getting stuck in tour state.

After exit, restore sensible manual navigation.

---

# 21. Reduced motion

Honor:

```css
@media (prefers-reduced-motion: reduce)
```

For users requesting reduced motion:

* reduce long fly-to transitions;
* remove unnecessary UI motion;
* shorten or replace camera easing;
* do not autoplay visually aggressive transitions.

The application should remain fully usable.

---

# 22. Labels

Use labels selectively.

Do NOT label 6,982 buildings simultaneously.

Prioritize:

```text
selected entity
tour stop
important landmarks
major POIs
```

Use HTML-based labels or the existing UI layer where appropriate.

Avoid expensive permanent 3D text.

If evaluating Three.js `CSS2DRenderer`, note that it is designed specifically for HTML labels attached to 3D objects, but only adopt it if it integrates cleanly with the R3F stack.

Drei HTML overlays may already satisfy the requirement.

Do not add another renderer without reason.

---

# 23. Minimap / orientation aid

M19 is the appropriate point to revisit the minimap.

First test whether users can orient themselves using:

```text
search
landmark labels
tour
existing camera controls
```

If orientation remains weak, add a simple 2D minimap.

Minimum useful minimap:

```text
BGC outline / major roads
current camera position
heading
selected destination
```

Do NOT create another full GIS renderer.

Do NOT add external map SDK dependencies unless proven necessary.

---

# 24. Mobile/narrow-screen UI

M20 will perform full mobile performance optimization.

M19 should still make the UI structurally responsive.

Use:

```text
bottom sheets
larger touch controls
collapsible search
compact mode selector
```

on narrow screens.

Avoid desktop sidebars squeezed onto phones.

---

# 25. Touch targets

Follow WCAG 2.2 AA minimum target-size guidance.

Interactive controls should normally meet or exceed:

```text
24 × 24 CSS px
```

with suitable spacing.

For important primary mobile controls, aim larger when layout permits.

Do not make tiny icon-only controls difficult to hit.

---

# 26. Keyboard accessibility

All non-3D UI functions must be keyboard operable.

At minimum:

```text
Tab
Shift+Tab
Enter
Space
Escape
Arrow keys where widget semantics require them
```

Do not create click-only controls.

---

# 27. Visible focus

Never remove focus outlines without an equivalent replacement.

Follow WCAG 2.2 Focus Visible requirements.

Use a clearly visible focus treatment for:

```text
buttons
search
results
tour controls
drawers/dialogs
settings
```

---

# 28. Do not obscure keyboard focus

Fixed overlays must not make the focused control invisible.

This matters because the application uses viewport-fixed UI.

Test keyboard navigation with:

```text
building panel open
search results open
tour interface open
mobile bottom sheet open
```

---

# 29. Dialogs and modal surfaces

Avoid modals for ordinary building information.

Use non-modal contextual panels where possible.

If a true modal is required—for example onboarding/help—follow WAI dialog behavior:

```text
focus enters dialog
Tab remains inside
Escape closes
focus returns appropriately
```

Prefer native semantic HTML where possible.

Do not add ARIA where native semantics already work.

---

# 30. Accessibility alternative to 3D-only interaction

Important functionality must not require accurately clicking a 3D building.

Provide equivalent UI through:

```text
search
tour list
place list / selected place navigation
```

A user who cannot precisely operate the canvas should still be able to explore known places.

---

# 31. Accessibility status messages

Loading, search selection, mode changes and important errors should be accessible to assistive technology where appropriate.

Examples:

```text
Central Square selected
Walk mode exited
Tour stopped
Unable to load nearby city data
```

Avoid announcing rapidly changing FPS/tile metrics.

# 36. Visual design system

Derive UI appearance from the completed M18 environment.

Create a small token system:

```text

text colors
accent
borders
radii
spacing

```

Do not scatter arbitrary CSS values throughout components.

CSS variables are sufficient.

A large component/design-system dependency is not required.

# 37. Maintain visual restraint

The 3D environment is already visually complex.

UI should therefore generally be:

```text
quiet
high contrast
compact
legible
translucent only where readability survives
```

Avoid:

```text
excessive glassmorphism
heavy gradients
large decorative cards
constant animation
```

---

# 38. Debug UI separation

Current runtime instrumentation remains valuable.

Move engineering information behind:

```text
?debug=1
```

or equivalent.

Debug mode may expose:

```text
FPS
draw calls
triangles
active tiles
active LODs
collision information
tile boundaries
height evidence
```

Production default:

hidden.

Do not delete M20's diagnostic capabilities.

---

# 39. Error states

Design explicit errors for:

```text
WebGL unavailable
world manifest failed
tile failed
LOD asset failed
unsupported interaction
```

Prefer graceful degradation.

Example:

```text
We couldn't load the 3D city.
Retry
```

Technical errors can be available under disclosure/debug mode.

---

# 40. Recovery

A failed optional landmark asset should not necessarily destroy the whole experience.

Where architecture permits:

```text
LOD1 failure
→ retain LOD2
```

instead of fatal viewer failure.

Tile failure:

identify affected region and provide retry.

Do not silently hide permanent failures.

---

# 41. Empty/search states

Handle:

```text
no search match
unknown building
building without detailed information
```

without inventing content.

Example:

```text
No matching place found.
```

not fabricated recommendations.

---

# 42. Fullscreen

Fullscreen can improve immersive use, but browser support differs.

Treat it as progressive enhancement.

Provide a fullscreen control only where the API is available.

Never make fullscreen mandatory.

---

Before installing any UI library, determine whether existing:

Do not add:


# 44. State architecture

```text

```

Do not synchronize everything globally.

Use the simplest state ownership that works with the actual post-M18 codebase.

# 63. UX acceptance tasks

A new user should be able to complete these without explanation:

1. Identify that the application represents BGC.
2. Find Central Square.
3. Navigate to it.
4. Learn basic available information.
5. Enter and exit walking mode.
6. Start a guided tour.
7. Exit a tour.
8. Share a selected place.
9. Find attribution/data methodology.
10. Recover from an accidental mode change.

If any of these require knowing implementation terminology, revise the UI.
